# ADR-0005：归档项目变更策略

- 状态：Accepted
- 决策日期：2026-09-01
- 决策编号：M1-CR-04
- Owner：产品 / 平台架构 / 安全

## 背景

M1 已提供项目归档与恢复，但“归档”究竟只冻结业务内容，还是同时冻结项目元数据和成员管理，尚未形成权威契约。M2 将进入资产与对象存储域；若不先固定语义，不同资源可能对归档状态作出不一致解释。

## 决策

项目归档后进入只读治理状态：

1. 允许读取项目、成员以及其既有资源。
2. 允许具备项目管理权限的主体恢复项目。
3. 允许既有受控删除流程继续执行；删除仍须满足权限、版本和审计要求。
4. 禁止新增或修改业务内容，包括 M2 资产、上传会话和对象关联。
5. 禁止修改项目名称、描述、code 及其他业务元数据。
6. 禁止添加、修改角色或移除项目成员。
7. 恢复项目后，归档前的成员关系和权限原样保留；恢复本身不得重算、扩张或收缩权限。

紧急移除成员不作为普通 API 的隐式例外。若出现账号失陷等安全事件，应使用独立的、显式授权且完整审计的安全响应流程；该流程须另行设计和验收。

## API 错误语义

- 对已归档项目执行上述禁止写操作时，返回 HTTP `409 Conflict`。
- Problem Details `code` 固定为 `PROJECT_ARCHIVED`。
- 响应不得泄露调用者无权获知的项目存在性；非成员或无权主体仍遵循既有 `404/403` 隐藏与授权语义，授权检查先于归档冲突判断。
- 并发请求以提交时状态为准：若项目在写入提交前已归档，则写入不得成功。
- 幂等重放不得绕过归档检查；仅可重放归档前已经成功提交的同一结果。

## M2 约束

M2 的资产、上传会话、Multipart 完成、对象绑定和清理 API 必须复用本 ADR，不得各自定义“归档后可写”的例外。对象存储中的物理清理属于受控生命周期动作，不等同于用户业务写入，但必须有审计、幂等和对账证据。

## 验收测试矩阵

| 场景 | 期望结果 |
|---|---|
| 读取已归档项目及成员 | 按既有权限成功 |
| 修改名称、描述或其他元数据 | `409 PROJECT_ARCHIVED` |
| 添加成员 | `409 PROJECT_ARCHIVED` |
| 修改成员角色 | `409 PROJECT_ARCHIVED` |
| 移除成员 | `409 PROJECT_ARCHIVED` |
| 创建或修改资产/上传会话 | `409 PROJECT_ARCHIVED` |
| 恢复项目 | 按权限成功，成员与角色保持不变 |
| 非成员访问已归档项目 | 保持既有隐藏语义，不因归档泄露存在性 |
| 归档与写入并发 | 最多一个与最终状态一致的结果，不产生归档后的新写入 |
| 幂等键重放 | 不绕过归档策略，不产生重复副作用 |

## 影响

该决策优先保证归档状态的一致性和可预测性，代价是归档后不能通过普通成员 API 立即撤销访问。安全事件处置必须走独立流程，避免在普通 API 中加入难以审计的隐式后门。

## 实施边界

本 ADR 先固化产品和架构语义。M1-CR-04 不为尚未存在的 M2 资产 API 编写占位实现；现有项目 API 与后续 M2 API 应在各自实现批次按本矩阵补齐自动化测试。
