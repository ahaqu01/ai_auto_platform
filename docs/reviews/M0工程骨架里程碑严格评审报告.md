## 1. 执行摘要

项目已经从纯设计进入可运行骨架阶段，完成了模块化单体仓库、FastAPI、Vue、Go Agent 骨架、PostgreSQL/Redis/MinIO 开发环境、基础企业/项目持久化和 OIDC JWT 验证。代码规模小、可读性尚可，现有测试、构建和迁移检查均能通过。

但严格按照现有 PRD、架构、详细设计和第一阶段验收文件评审，当前成果距离“身份、企业、项目里程碑完成”仍有明显差距：

1. 文档定义的是 BFF Session Cookie + Keycloak 单一身份源，代码实现的是 API 直接接收 Bearer Token，架构裁决没有被执行。
2. Keycloak、真实登录流程、成员邀请、角色授权、审计、幂等、RLS、乐观锁和项目生命周期均未落地。
3. 仓库宣称 OpenAPI-first，但受控 OpenAPI 仅有健康接口，且路径前缀与运行时不一致。
4. 验收结果存在测试覆盖不足造成的假阳性，不能作为里程碑签字证据。
5. 没有 CI、远程仓库、分支保护、CODEOWNERS、Staging、镜像、部署与回滚体系。
6. 当前时间计划建立在 5—6 人团队前提上，与实际执行能力、依赖风险和已完成比例没有建立对应关系。

因此，本次不能批准直接进入“资产/Agent/任务中心”大规模开发。必须先完成 M0 整改门，随后以 M1 身份与租户闭环重新验收。

## 5. Blocker 问题

### BLK-01：身份架构裁决与实现不一致

**证据**：

- `docs/design/05-设计审计与修订记录.md` 的 DD-015 明确规定 Web 使用 BFF Session Cookie，Token 由 BFF 持有。
- `apps/web/README.md` 重申不能把 Refresh Token 放入 LocalStorage。
- 当前 API 直接要求浏览器提交 Bearer Token，Web 尚无 BFF、Session、CSRF 和登录回调。

**影响**：后续前端一旦按 Bearer 模式扩展，切换 BFF 时所有 API 客户端、路由守卫、刷新和退出逻辑都要返工；若把 Refresh Token 暴露给浏览器，会扩大 XSS 风险。

**裁决**：在 M1 开发前必须完成 ADR，二选一并冻结：

1. 推荐：同仓 BFF + HttpOnly/Secure/SameSite Cookie，API 对浏览器不暴露 Refresh Token。
2. 若明确采用 SPA PKCE，则必须修订 DD-015、威胁模型、Token 存储和 CSRF/XSS 策略，并由安全评审签字。

### BLK-02：受控 OpenAPI 与运行时 API 不一致

**证据**：`packages/contracts/openapi.yaml` 只有健康接口；企业、项目、认证、安全方案均不存在。文件声明 server `/api/v1`，同时路径又是 `/health/live`，组合后与运行时 `/health/live` 不一致。

**影响**：无法生成可信客户端、无法做契约兼容检查，“OpenAPI-first”名不副实；前后端可能各自演进。

**整改**：确定唯一事实源。当前阶段推荐以 FastAPI 运行时 OpenAPI 为事实源，在 CI 导出并与受控快照比较；禁止手工维护另一份不完整契约。

### BLK-03：身份验收报告存在假阳性

**证据与复核**：

- AUTH-06 声称“不再接收 owner_email/owner_display_name”，但 Pydantic 默认忽略多余字段，旧字段仍会被静默接受；测试只验证 OpenAPI 没展示字段，没有验证请求应被 422 拒绝。
- AUTH-05 只验证单请求重复同步，未验证并发首次登录。当前 `_synchronize_user` 是“先查再插”，并发请求中失败者会返回 `409 IDENTITY_CONFLICT`，而不是复用已创建用户。
- AUTH-08 只验证一个项目列表读接口，没有覆盖企业详情、项目写入、猜测 UUID、跨角色操作等矩阵。

**影响**：验收签字无法证明声明的行为，继续使用同类方法会把“测试通过”误当成“安全成立”。

**整改**：撤销该切片的“完整通过”状态，改为“部分通过/待整改”；补充严格 DTO、并发 PostgreSQL 测试和资源×角色×动作授权矩阵。

### BLK-04：不存在可用的真实身份闭环

**证据**：Compose 没有 Keycloak；没有 Realm/Client IaC、登录回调、真实 JWKS 轮换、测试用户或端到端 Token 测试。无 OIDC 配置时 API 把运维错误伪装成普通 401。

**影响**：系统当前不能由真实用户登录使用，认证服务配置错误也不会被 readiness/告警发现。

**整改**：Keycloak 可重复初始化、真实 Token E2E、readiness 失败、JWKS 超时/轮换测试必须进入 M1 准入门。

### BLK-05：没有持续集成和远程代码资产

**证据**：Git 仅在单台开发服务器；没有 remote、PR、分支保护、CODEOWNERS、CI、制品或备份。

**影响**：服务器磁盘或误操作可导致代码丢失；当前所有“门禁”依赖人工执行，无法证明每次提交都通过。

**整改**：在继续大功能前建立私有远程、保护主分支和最小 CI。该项属于 M0 退出条件。

## 6. Critical 问题

### CRT-01：实现数据模型没有遵守文档通用规范

设计要求可变聚合包含 `version`、软删除/状态、约束、审计和乐观锁；当前 users、organizations、projects 均无 version，organizations 无状态/slug，项目也没有 API 层归档/恢复。设计要求 `varchar + check constraint`，迁移中的 role/status 只是 String，缺少数据库 CHECK。

结果是文档中的并发保护和非法状态防御尚不存在。进入更多业务表前必须先建立统一模型基类和迁移约定。

### CRT-02：认证依赖自行 commit，破坏业务事务边界

`_synchronize_user` 在依赖解析阶段执行 commit，之后企业创建又执行第二次 commit。身份投影、业务操作、审计和 Outbox 无法组成一个明确事务；每次请求还可能因资料变化产生写事务。

应把用户同步设计为独立幂等服务或受控 upsert，明确事务边界；业务命令必须由应用服务控制一次提交，而不是路由和依赖随处 commit。

### CRT-03：并发身份同步不正确

同一新 Subject 的两个并发请求会竞争唯一约束，失败请求直接 409。邮箱全局唯一还会让身份供应商中的邮箱变更或重复邮箱产生不可预测冲突。

需要 PostgreSQL 原子 upsert、冲突后重查，并明确“同邮箱不同 Subject”是合并、拒绝还是人工关联。必须写决策记录和并发测试。

### CRT-04：领域层与 ORM/API 脱节

最后 Owner、项目归档等规则只存在 dataclass 和单元测试，实际 API/ORM 没有成员变更、归档接口，也没有映射或应用服务调用这些领域对象。

这会形成“规则测试通过但生产路径绕过规则”的假安全。需要选择一种一致方式：领域实体驱动 Repository，或明确采用事务脚本并把规则放在应用服务/数据库约束中。

### CRT-05：多租户纵深防御未实现

设计多次把 PostgreSQL RLS 列为 P0 Blocker 修订项；当前只在两个查询中手写成员关系过滤，没有 RLS、连接池上下文、复用测试和管理员专用角色。

在资源种类增加前必须完成授权策略组件和 PostgreSQL 集成测试。否则每新增接口都可能遗漏组织过滤。

### CRT-06：DoD 与实际交付流程失真

原计划 DoD 要求至少一人评审、OpenAPI/配置同步、日志指标 Trace、Staging、漏洞扫描；现有提交均不具备这些条件，却被描述为“完成”。这会持续制造状态失真。

整改方式不是降低安全标准，而是区分：

- 本地开发完成。
- 技术评审完成。
- Staging 验收完成。
- 里程碑正式完成。

## 7. Major 问题

### MAJ-01：PRD、架构、详细设计重复且缺少权威性标记

5,613 行 Markdown 中存在大量重复描述，但没有“当前有效版本、被替代版本、最后评审提交、负责人”。设计审计修订了 V1.0，但原文没有显著标出哪些段落已被 V1.1 覆盖。

建议建立文档索引和状态字段：Draft/Approved/Superseded，并为关键裁决使用 ADR。

### MAJ-02：交接文档已经过期

交接文档仍写“身份认证尚未接入”和下一步从 JWT 开始，未记录 `0386d6b`、迁移 `20260821_02` 和新增 16 项测试。交接文档不能同时承担历史日志和当前状态。

建议新增短小的 `CURRENT_STATUS.md` 作为唯一当前状态源；交接文档按日期归档。

### MAJ-03：第一阶段 8 周计划不可信

计划包含身份、邀请、项目、OSS 20GB 分片、mTLS、Temporal、Agent、日志、审计、PITR、压测、渗透、IaC、监控等，适用于已有 5—6 人团队和成熟基础设施。当前实际是一套单机骨架，无 CI/Keycloak/Temporal/OSS 业务/Agent 通信。

应改为门禁式里程碑，不再按旧 Sprint 编号宣称完成；时间估算必须基于可用人力重新计算。

### MAJ-04：测试体系主要是 SQLite 和 Fake

API 集成测试使用 SQLite，认证使用 Fake Verifier，真实 PostgreSQL 只做迁移。SQLite 不会覆盖 PostgreSQL 锁、upsert、RLS、事务隔离、约束差异。JWKS 测试没有覆盖真实 HTTP、Key 轮换、缓存失效和超时。

### MAJ-05：覆盖率分布不合理

总覆盖率 81% 达到文档阈值，但认证依赖只有 55%，项目 API 69%，请求上下文 0%。总百分比掩盖了关键路径缺口。应对 auth/authorization/transaction 设置更高的分支覆盖和场景门禁。

### MAJ-06：API 错误与协议不完整

- 401 没有明确验证 `WWW-Authenticate: Bearer`。
- 未处理的异常不保证统一 Problem 响应。
- 列表没有分页。
- 请求 DTO 未统一 `extra="forbid"`。
- 没有 Idempotency-Key、If-Match、审计事件。
- 缺少 readiness 和依赖健康检查。

### MAJ-07：运维配置仍是开发演示级

- Compose 把数据库和 MinIO 口令明文提交。
- 没有 `.env.example` 与启动前配置校验。
- Compose `version: 3.9` 已废弃并持续告警。
- API 仍由 nohup 启动，没有容器/systemd、日志轮转或自动恢复。
- 没有 Dockerfile、镜像版本、SBOM、监控和备份。

### MAJ-08：前端尚不是产品切片

前端只有健康首页和一个测试；没有 API Client、登录、错误边界、企业/项目页面、路由守卫、可访问性和浏览器矩阵。生产构建成功不等于用户故事完成。

### MAJ-09：Agent 和 Workflow 只有占位

Agent 只读取配置，Workflow Worker 只有 4 行 README。当前不能验证平台最核心差异化——本地服务器和真实设备执行。

### MAJ-10：跨平台文档交付未经验证

Windows 自带 tar 解压 Git 快照时多个中文文件名产生错误或乱码。虽然不是业务代码故障，但会影响 Windows 开发者、备份和某些 CI 制品。

建议保留中文标题，但关键受控文档文件名改用 ASCII slug，或至少在 Windows/Linux CI 中验证归档解压与链接。
