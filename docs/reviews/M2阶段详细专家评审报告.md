## 3. Bugbot 缺陷复核

### P1-BUG-01：缺失对象对账会永久饿饿后续资产

- 位置：`apps/api/src/platform_api/modules/artifact/maintenance.py:189-224`
- 证据：每次都按 `updated_at, id` 从头选取 `AVAILABLE` 资产，固定 `.limit(batch_size)`；对健康对象执行 HEAD 后不更新任何扫描游标或时间。
- 影响：当 AVAILABLE 资产超过默认 100 个时，最旧的 100 个健康资产会在每次迭代中被重复检查，其后资产永远无法进入对账范围，对象缺失可长期不被发现。
- 测试缺口：`test_m2_07_maintenance.py` 只覆盖小数据集，没有 `batch_size + 1` 或多轮公平性用例。
- 建议：增加持久化游标/分片，或对成功检查记录 `last_reconciled_at`，并用 `SKIP LOCKED` 和多轮测试保证公平性。

### P1-BUG-02：孤儿对象清理在前 N 个已知对象后饿饿

- 位置：`apps/api/src/platform_api/modules/artifact/maintenance.py:226-275`
- 证据：对象列举每轮从 `v1/o/` 起点开始；`seen` 在查询数据库是否已知之前就加一，到 `batch_size` 立即停止。
- 影响：如果字典序靠前的 100 个老对象都是合法已知对象，第 101 个及其后的真实孤儿永远不会被检查或删除。
- 建议：持久化 OSS continuation token/扫描游标，对整个 keyspace 轮询；`batch_size` 应限制实际删除/数据库操作量，不应让已知对象占满每轮额度。

### P2-BUG-03：API 允许 3600 秒签名，实际 Gateway 只允许 900 秒

- 位置：`apps/api/src/platform_api/api/artifacts.py:74-75`、`apps/api/src/platform_api/api/upload_sessions.py:123-125`、`apps/api/src/platform_api/modules/artifact/s3_gateway.py:151-158`
- 证据：Pydantic 请求模型声明 `le=3600`，但 `_presigned()` 对任何大于 900 的值抛出 `INVALID_REQUEST`；API 又将其统一映射为 503。
- 实测：在当前 Demo API 容器直接调用 OSS Gateway 的 3600 秒签名，结果为 `StorageGatewayError INVALID_REQUEST`。
- 影响：符合 OpenAPI 的请求却返回“存储不可用”，破坏合同可信度和故障诊断。
- 建议：单一常量统一 API/OpenAPI/Gateway 上限；若安全策略确定为 900 秒，API 应在入口返回 422，不应映射为 503。

### P2-BUG-04：Web 资产列表丢弃分页游标

- 位置：`apps/web/src/platform.ts:94`、`apps/web/src/views/AssetsView.vue:26-32`
- 证据：Web 固定请求 `limit=100`，只保存 `items`，忽略 API 返回的 `next_cursor`；界面没有“加载更多”或分页入口。
- 影响：一个项目超过 100 个可见资产后，旧资产无法通过管理台查看详情或发起授权下载。
- 建议：实现游标翻页/连续加载，并增加 `next_cursor != null` 的前端测试。

### P2-BUG-05：完成接口校验 Idempotency-Key 但未写入幂等记录

- 位置：`apps/api/src/platform_api/api/upload_sessions.py:630-669`
- 证据：接口强制要求并校验 `Idempotency-Key`，但没有调用 `begin_idempotent_command()` / `complete_idempotent_command()`；实际只依赖 upload 状态和唯一 artifact 约束防重。
- 影响：同一 key 不同 payload 不会被幂等子系统识别为冲突，审计语义与其他命令不一致。
- 建议：要么将 completion 接入通用幂等命令记录，要么删除虚假的 key 要求并在 ADR/OpenAPI 中明确“资源状态幂等”。

### P3-BUG-06：上传作业期间范围选择锁定不完整

- 位置：`apps/web/src/views/AssetsView.vue:113-115`
- 证据：组织和项目选择框只在 `UPLOADING` 时禁用，在 `HASHING` 和 `COMPLETING` 时仍可切换。
- 影响：Controller 内部范围不会被改写，数据不会跨租户；但完成后页面可刷新到另一项目，造成“上传成功但列表看不到”的用户困惑。
- 建议：在 `HASHING/UPLOADING/PAUSED/COMPLETING` 整个作业周期锁定范围，或明确显示 Controller 已绑定的组织/项目。

## 4. Security Review 安全复核

### P1-SEC-01：API 和维护 Worker 共用数据库超级用户凭据

- 位置：`deploy/staging/.env.example:1-10`、`deploy/staging/docker-compose.yml:67-108`、`apps/api/src/platform_api/common/tenancy.py:15-30`
- 证据：Compose 中 PostgreSQL 由 `POSTGRES_USER=platform` 初始化，该用户默认是超级用户；API、迁移和维护 Worker 共用同一 `DATABASE_URL`。API 在通过认证后使用 `SET LOCAL ROLE platform_runtime` 约束常规业务请求，但进程仍持有可还原为超级用户的登录凭据；维护 Worker 直接依赖这一身份跨租户读写。
- 影响：任一 API/Worker RCE、驱动漏洞或未包装 SQL 路径都可绕过 `FORCE RLS`，影响全部租户。
- 建议：拆分 migration owner、API login role 和 maintenance role；API 登录角色应 `NOSUPERUSER NOBYPASSRLS`，不应能切回 owner；维护使用限定表/操作的专用角色或经审计的 `SECURITY DEFINER` 函数。

### P2-SEC-02：OSS 仍使用长期 RAM AccessKey

- 证据：Staging 通过权限 `0600` 的外部 env 文件注入新 Key，仓库扫描未发现真实 AK/Secret；但运行时仍是长期 AccessKey，非 STS。
- 影响：主机、容器环境或备份泄露后，凭据可在轮换前持续使用。旧 Key 因其他服务占用不在本项目可删除范围，不影响“本项目已切换新 Key”的事实，但仍是账号级残余风险。
- 建议：迁移到 ECS RAM Role/STS，限制 bucket + `v1/o/*` + 必要动作，建立自动轮换和泄露响应清单。

### P3-SEC-03：资产可用不包含恶意软件扫描

- 位置：`apps/api/src/platform_api/api/upload_sessions.py:743-770`
- 证据：强校验只比对 size 和 SHA-256，通过后直接写入 `security_scan_status=NOT_REQUIRED` 且 `status=AVAILABLE`。
- 影响：对 M2 的“存储与下载”限定范围可接受，但如果 M3 的 Agent、训练或解压流程直接消费 AVAILABLE 对象，会把未扫描文件带入执行边界。
- 建议：M3 前增加“可存储”与“可执行/可解压”的独立状态门禁；高风险消费者只接受 `CLEAN`。

### 安全正向结论

- 未在受控 Git 文件中发现真实阿里云 AccessKey、私钥或非占位密码。
- 对象 Key 使用不含租户和文件名的随机识别，且端口层与 RLS 同时校验组织/项目。
- OSS 网关对 HTTPS、DNS 解析、socket peer、TLS SNI/hostname 和重定向有明确防护。
- 预签名 URL 未进入持久化、审计详情或日志，并对 `repr` 做了脱敏。
- 下载只对 `AVAILABLE` 资产签名；QUARANTINED/DELETING/DELETED 不可下载。

## 7. 整改优先级和复验门禁

### Gate A：关闭 P1

1. 修复缺失对象对账和孤儿清理的公平遍历；提供大于两倍 batch size 的多轮测试。
2. 拆分 migration/API/maintenance 数据库身份；用真实 PostgreSQL 证明 API 登录身份无法绕过 RLS，维护身份只有必要权限。

### Gate B：关闭 P2

1. 统一预签名 TTL 合同和错误映射。
2. 完成资产列表游标分页。
3. 统一 completion 幂等语义。
4. 输出 OSS 向 STS/实例 RAM Role 迁移计划和可执行的轮换记录。

### Gate C：回归与签署

- 执行全量 API/Web/PostgreSQL/security CI。
- 使用真实 MinIO 执行批次超限对账，并在受控 OSS Staging 上执行至少一轮孤儿翻页清理。
- 产品、技术、安全、QA 重新签署《M2 详细复评整改记录》。
- 不移动 `m2-accepted`；整改完成后可创建新的 `m2-review-remediation-accepted` 标签。

## 8. 最终意见

M2 不是“重做”状态，主功能和真实存储链路已经建立；但它也不应因为 CI、E2E 和四方签署已完成就被认定为“无条件生产就绪”。当前最合理的工程处置是保留历史验收标签，建立独立整改分支，按 Gate A → Gate B → Gate C 关闭新发现，再开始依赖资产的 M3 执行与训练链路。
