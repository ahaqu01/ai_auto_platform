## 1. 执行摘要

M0R-03、04、05 显著改善了工程基线：OpenAPI 已由运行时确定性生成；Staging/Production 有了基本配置失败保护；PostgreSQL 约束、事务、级联和迁移开始获得真实数据库证据。三个阶段均保留了实现前失败、实现后转绿和全量回归记录，测试优先流程总体可信。

但本轮严格评审发现两个 P1 和多个 P2，其中 PostgreSQL 测试目标库保护不足具有潜在破坏性，必须在再次运行 M0R-05 测试前优先整改。配置校验也不足以保证部署配置可用或阻止敏感地址误配。部分验收文档把“存在启发式保护”“直接模型测试”写成了更强的安全和 API 证据，结论需要降级。

因此，本里程碑不能晋升到 `REVIEWED`、`VERIFIED_STAGING` 或 `ACCEPTED`，也不应直接继续新增 M1 业务能力。

## 5. 严格评审发现

### P1-01：测试数据库保护不足，存在破坏性误用风险

- 位置：`apps/api/tests/postgresql/conftest.py` 目标 URL 校验及 schema 创建/清理逻辑；迁移降级测试。
- 现状：只拒绝精确 `APP_ENV=production` 或数据库名包含 `production`。数据库名为 `platform`、`prod`、`live`、`business` 且 APP_ENV 未设置时可以通过。
- 后果：夹具随后执行 Alembic upgrade/downgrade、`CREATE SCHEMA` 和 `DROP SCHEMA ... CASCADE`。误配到业务集群时可能改变迁移状态或破坏对象。
- 证据缺口：PG-01 标记“通过”，但实现只是弱命名启发式。
- 整改要求：在再次执行 PostgreSQL 集成测试前加入显式双重确认、专用测试数据库/角色、数据库身份检查和非超级用户约束；迁移 downgrade 只能在一次性数据库中执行。

### P1-02：部署配置可通过校验但运行时不可用

- 位置：`apps/api/src/platform_api/settings.py`。
- 现状：主要检查非空、loopback 和两个 HTTPS scheme，没有完整验证 URL 语法、hostname、port 和支持协议。
- 可通过的错误示例：SQLite database URL、`redis_url=garbage`、`temporal_address=garbage`、`https:///realms/x`、无 hostname 的 OSS endpoint。
- 后果：部署被错误认为配置有效，直到首个请求或后台任务才失败。
- 整改要求：为每个字段建立结构化类型/解析器和允许协议；验证 hostname、port、路径语义和凭证要求。

### P2-01：PostgreSQL 未覆盖真实 API 持久化链路

- 位置：`apps/api/tests/postgresql/test_postgresql_integration.py`。
- 现状：测试直接使用 engine、session 和 ORM model，没有通过 FastAPI、认证依赖、应用服务或租户查询。
- 影响：SQLite 与 PostgreSQL 在 API 事务边界、异常映射和查询语义上的差异仍未得到证明。
- 验收纠正：原“API 全量（包含 PostgreSQL）”应解释为“同一 pytest 运行包含直接 PostgreSQL 测试”，不能解释为“API 已运行在 PostgreSQL 上”。

### P2-02：并发测试可能把无关 IntegrityError 当成目标冲突

- 位置：项目 code 并发写测试。
- 现状：捕获任意 `IntegrityError` 后返回 conflict。
- 影响：NOT NULL、FK、CHECK 等错误也可让测试错误通过。
- 整改要求：断言 PostgreSQL SQLSTATE `23505` 和目标约束名 `uq_projects_organization_id`。

### P2-03：迁移降级完整性断言不足

- 位置：迁移 downgrade/base/upgrade 测试。
- 现状：降到 base 后只检查 `users` 表不存在。
- 影响：残余表、索引、约束、类型、序列或触发器可能未被发现。
- 整改要求：对 schema 对象清单建立 base allowlist；验证单 head、所有版本和完整对象清理。

### P2-04：调用者身份契约证明过弱

- 位置：`apps/api/tests/test_openapi_contract.py`。
- 现状：将整个 schema 序列化后搜索 `user_id`。
- 影响：`actor_id`、`owner`、`subject` 等别名可绕过；响应模型中合法出现 `user_id` 又会误报。
- 整改要求：逐 operation 检查 path/query/header/request-body 输入字段的禁止身份集合，并与真实 401/403/404 租户行为测试分开验收。

### P2-05：公网依赖地址的 SSRF/误路由保护不完整

- 位置：Settings `_is_local_host` 与公网 endpoint 校验。
- 现状：只拒绝 loopback。
- 影响：link-local、云元数据地址、unspecified、reserved、multicast，以及 DNS 解析到敏感网段仍可能被接受。
- 整改要求：对 OIDC/OSS 公网 endpoint 禁止 link-local/metadata/unspecified/reserved；运行时 HTTP 客户端还需校验 DNS 解析结果和重定向目标。内网 endpoint 必须采用独立策略，不能与公网规则混用。

### P3-01：Settings 可在构造后绕过校验

- 位置：Settings model config。
- 现状：对象可变且未启用 assignment validation。
- 影响：已通过校验的实例可被改成 Production/local URL 组合。
- 整改要求：优先冻结 Settings；若确需可变，启用 assignment validation 并重新执行跨字段校验。

### P3-02：OpenAPI 稳定性只证明同环境重复性

- 位置：OpenAPI 字节稳定性测试。
- 现状：两次子进程继承同一环境。
- 影响：配置驱动的 schema 分支在不同机器/环境中可能漂移。
- 整改要求：导出使用净化、显式的 schema-generation 环境，或保证 app schema 构造完全不依赖运行配置。

### P3-03：过程门禁仍不完整

- 无私有远端仓库、受保护 PR 和 CODEOWNERS。
- 无 CI 强制执行 OpenAPI、配置和 PostgreSQL 测试。
- 无独立 PostgreSQL 测试角色和一次性数据库。
- 无 Staging 真实配置启动证据。
- 两个专项子评审在 IP 变更期间依据本地保留文件完成；主评审恢复连接后已核对服务器 HEAD、干净工作区和关键代码位置。
