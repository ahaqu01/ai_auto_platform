# M0R-03 OpenAPI 单一事实源轻量评审报告

> 评审日期：2026-08-21
> 评审对象：提交 `6acd823`
> 结论：有条件通过，保持 `IMPLEMENTED_LOCAL`

## 结论摘要

本阶段实现了运行时模式的确定性导出、受控 JSON 快照、漂移检查和契约断言。测试遵循先失败后实现的顺序，失败原因与缺失功能一致；API、Web、Agent 和迁移回归均通过。变更没有修改业务逻辑、数据库结构或部署配置。

当前不能标记为 `REVIEWED` 或 `ACCEPTED`：尚无独立代码评审、受保护 PR、CI 和 Staging 证据；现有门禁只能发现“快照是否过期”，不能自动判定相对上一版本是否发生破坏性变更。

## 符合预期的部分

1. 测试先于实现，预期失败为快照缺失，不是环境或导入损坏。
2. 导出采用排序键、固定缩进、UTF-8 和结尾换行，重复输出字节稳定。
3. 快照与 FastAPI 运行时模式深度相等，消除了手工 YAML 与运行时的双重事实源。
4. 测试覆盖必要路径、Bearer 安全声明、调用者身份和唯一 operation ID。
5. `--check` 是只读检查，适合直接接入本地门禁和 CI。
6. 删除旧 YAML 已纳入 Git，回滚路径明确。

## 发现与分级

### P1：缺少跨版本兼容性检测

原计划称“破坏性变更检测通过”，但当前只验证当前运行时与当前快照一致。删除路径、收紧字段或改变响应结构，只要重新生成快照就能通过。因此新增 M0R-03A，在 CI 中对 PR 与目标分支快照做兼容性比较。

### P2：自动化门禁尚未落地

导出检查和契约测试目前依赖人工执行。M0R-02 必须加入 `scripts/export_openapi.py --check` 和契约测试，并保留 PR 失败日志。

### P2：历史迁移格式策略不明确

全目录 Ruff 格式检查会命中两份基线历史迁移。纯格式改写已执行迁移会制造无业务价值的审计噪声。计划调整为：历史迁移不可变；新迁移在首次部署前通过全部检查；CI 对应用源码和历史迁移采用明确的差异化规则。

### P3：上游 TestClient 弃用警告

API 回归有一条 FastAPI/Starlette TestClient 上游弃用警告，不影响当前功能。后续依赖治理中跟踪兼容升级，不在本切片临时升级依赖。

## 风险判断

- 运行时与快照漂移风险：低。
- 未识别破坏性 API 变更风险：中，待 M0R-03A。
- 人工漏跑检查风险：中，待 M0R-02。
- 本次变更引入运行时回归风险：低，导出器不在服务启动路径中。

## 评审决定

1. M0R-03 保持 `IMPLEMENTED_LOCAL`。
2. 新增 M0R-03A，随 M0R-01/M0R-02 落地跨版本兼容性门禁。
3. 远端仓库尚未提供时，下一工作包为 M0R-04，之后为 M0R-05、M0R-06、M0R-07。
4. M1 开始前必须完成 M0R-01、M0R-02、M0R-03A，并补齐独立评审和 Staging 证据。
