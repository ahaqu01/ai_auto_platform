## 1. 修订原则

1. 先关闭破坏性和部署可用性风险，再进行文档治理或新增业务能力。
2. 每个整改包仍执行：验收标准 → 预期失败测试 → 实现 → 本地验证 → Bugbot → Security Review → 独立人工评审 → Staging/CI 证据。
3. 评审发现必须有稳定编号、负责人、提交和关闭证据；不得仅修改验收文案后关闭代码风险。
4. 验收声明只能描述测试真正证明的范围。
5. M0R-05R-01 完成前暂停迁移 downgrade 测试。

## 3. 整改包验收与测试要求

### 3.1 M0R-05R-01 测试数据库保险丝

实现前测试：

- 未设置显式 opt-in sentinel 时拒绝。
- 数据库名为 `platform`、`prod`、`production`、`live` 时拒绝。
- APP_ENV 缺失、大小写变化或 Production 时均不能弱化保护。
- 当前角色为 superuser 或不符合专用测试角色时拒绝。
- 实际 current_database/current_user 与期望不一致时拒绝。

实现要求：

- CI 创建一次性测试数据库和最小权限角色。
- 普通约束/API 测试可以使用随机 schema；downgrade 往返只能使用一次性独占数据库。
- 清理只能命中本次生成的 schema/database 标识，并有二次断言。

### 3.2 M0R-04R 配置整改

实现前测试：

- SQLite DB URL、无 hostname HTTPS、非法 Redis/Temporal 地址均拒绝。
- OIDC/OSS public endpoint 的 loopback、link-local、metadata、unspecified、reserved 地址拒绝。
- DNS 解析或重定向到敏感地址的运行时客户端策略有测试。
- 构造后修改配置失败。

实现要求：

- 使用结构化 URL 类型或专用解析器。
- 每个字段定义允许 scheme、hostname、port、path、TLS 要求。
- public 与 internal endpoint 使用不同策略。

### 3.3 M0R-05R-02/03 PostgreSQL 证据补强

- 并发唯一冲突断言 SQLSTATE `23505` 和约束名。
- downgrade base 后枚举 tables、indexes、constraints、types、sequences、triggers，并与 allowlist 比较。
- FastAPI dependency override 使用 PostgreSQL session；至少覆盖认证用户同步、创建企业、创建/读取项目、非成员隔离和事务回滚。
- 验收报告明确区分直接数据库测试和 API-on-PostgreSQL 测试。

### 3.4 M0R-03R OpenAPI 整改

- 逐 operation 检查 path/query/header/cookie/body 输入字段。
- 禁止身份字段集合至少含 user_id、actor_id、subject、owner_id，并允许按 API 语义审批例外。
- OpenAPI Bearer 声明不替代运行时 401/403/404 测试。
- 导出子进程使用显式净化环境；跨环境输出必须一致。

## 4. 评审流程修订

每个整改包进入 REVIEWED 前必须具备：

1. 验收标准与红灯证据；
2. 代码差异与测试映射；
3. Bugbot 复审结果；
4. Security Review 结果；
5. 人工评审对误报、漏报和破坏性边界的确认；
6. 未关闭问题及风险接受人。

任何 P1 未关闭时，不得合并或继续依赖该能力开发。

## 5. 验收流程修订

### IMPLEMENTED_LOCAL

- 专项测试和全量回归通过。
- 本地敏感信息扫描和差异检查通过。
- 验收结论不得出现“已安全”“已防止生产误用”等超出证据的表述。

### REVIEWED

- 双专项复审 P1/P2 为 0。
- 至少一名非作者人工评审。
- 所有发现均有关闭提交或批准例外。

### VERIFIED_STAGING

- 使用专用、一次性测试数据库和角色。
- Staging 配置来自 Secret Manager/受控注入，不写入仓库或日志。
- 不在共享 Staging 业务数据库执行 downgrade。

### ACCEPTED

- CI 在受保护 PR 连续成功至少三次。
- 证据包包含 commit、测试输出、数据库身份、镜像摘要、配置来源和签字。
- 产品、技术、QA 签字；配置、身份、数据库相关包还需安全签字。
