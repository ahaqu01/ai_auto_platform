# 里程碑后开发、评审与验收计划

> 计划版本：V2.0  
> 生效日期：2026-08-21  
> 基线：评审提交 `0386d6b`  
> 状态：拟批准  
> 替代关系：本计划取代 `docs/design/04-第一阶段迭代任务与验收标准.md` 中从当前日期开始的 Sprint 排期和“完成状态”解释；原文保留为产品范围与验收场景库。

## 1. 计划修订原则

1. 不再以“代码写完”代表里程碑完成。
2. 每个切片严格执行：验收标准 → 失败测试 → 实现 → 独立评审 → Staging 验收。
3. 先完成横切基础能力，再增加业务域。
4. 所有安全和多租户断言必须在 PostgreSQL/真实 IdP 环境验证。
5. 时间承诺必须在确认可用人数后给出；本计划以门禁和工作包排序，不虚构日期。
6. 任何文档与代码冲突，以 Approved ADR、运行时契约和当前计划为准。

## 2. 状态模型

每个工作包只能处于以下状态之一：

```text
DRAFT
→ READY
→ TESTS_RED
→ IMPLEMENTED_LOCAL
→ REVIEWED
→ VERIFIED_STAGING
→ ACCEPTED
```

状态含义：

| 状态 | 含义 |
|---|---|
| DRAFT | 需求或技术方案尚未满足准入 |
| READY | 验收标准、契约、权限、风险、测试环境已评审 |
| TESTS_RED | 测试先写并以预期原因失败 |
| IMPLEMENTED_LOCAL | 本地实现使测试转绿，但尚未独立评审 |
| REVIEWED | 代码、架构、安全和测试证据已评审 |
| VERIFIED_STAGING | 在同构 Staging 使用真实依赖验证 |
| ACCEPTED | 产品、技术、QA 对验收证据签字 |

禁止从 IMPLEMENTED_LOCAL 直接标记 ACCEPTED。

## 3. M0-R：工程基线整改门

### 3.1 目标

把当前单机工程骨架升级为可多人协作、可重复验证、契约一致的研发基线。

### 3.2 工作包

| ID | 工作包 | 前置 | 验收标准 |
|---|---|---|---|
| M0R-01 | 私有远程仓库、分支保护、CODEOWNERS | 用户提供仓库/权限 | 主分支禁止直接推送，至少一人评审 |
| M0R-02 | CI 基线 | M0R-01 | PR 自动执行 Ruff、pytest+coverage、Alembic check、Vitest/build、npm audit、Go vet/race |
| M0R-03 | OpenAPI 单一事实源 | 无 | 运行时导出、受控快照、破坏性变更检测通过 |
| M0R-04 | 配置基线 | 无 | `.env.example`、启动校验、Compose 无 obsolete 告警、无非开发默认值误用 |
| M0R-05 | PostgreSQL 集成测试夹具 | Compose | 并发、约束、事务和迁移测试运行于 PostgreSQL |
| M0R-06 | 文档治理 | 无 | 文档索引标明 Owner、状态、版本、替代关系；CURRENT_STATUS 与 HEAD 一致 |
| M0R-07 | API 进程托管 | 配置基线 | 重启自动恢复、日志轮转、health/readiness 可区分 |

### 3.3 M0-R 验收门

- CI 在受保护 PR 上连续成功至少 3 次。
- 空库升级到 head、head 降一级再升级通过。
- OpenAPI 快照无未解释差异。
- 当前敏感信息扫描无真实凭证。
- Linux 和 Windows 均可检出、构建或正确读取文档清单。
- Blocker：0；Critical 必须有已批准的短期整改期限，且不能影响 M1。

## 4. M1：真实身份与租户闭环

### 4.1 架构裁决门

开发前先提交并批准：

- ADR-0002：BFF Session Cookie 与 SPA PKCE 的最终选择。
- ADR-0003：Keycloak Subject、邮箱变更、账号合并和多 Issuer 策略。
- ADR-0004：应用授权与 PostgreSQL RLS 的职责边界。
- 身份和租户威胁模型。

### 4.2 工作包顺序

| 顺序 | ID | 工作包 | 核心验收 |
|---:|---|---|---|
| 1 | M1-01 | Keycloak Compose 与 Realm IaC | 重建后 Realm/Client/Role 可重复导入，无真实密钥入库 |
| 2 | M1-02 | 真实登录与会话 | 浏览器登录、刷新、退出、过期、吊销完整通过 |
| 3 | M1-03 | CurrentUser 并发同步整改 | 20 个并发首次请求只产生一个用户，全部成功或返回设计允许结果 |
| 4 | M1-04 | DTO/错误/契约基线 | extra 字段拒绝；401/403/404/409 和 WWW-Authenticate 契约固定 |
| 5 | M1-05 | 企业成员邀请与 RBAC | Owner/Admin/Member 权限矩阵全部自动化 |
| 6 | M1-06 | 最后 Owner 生产路径 | 并发降级/移除不能产生无 Owner 企业 |
| 7 | M1-07 | 项目完整生命周期 | CRUD、归档、恢复、成员、分页、乐观锁 |
| 8 | M1-08 | 审计、幂等和 Outbox 基线 | 关键写操作与审计/事件同事务，重复请求不重复创建 |
| 9 | M1-09 | 租户纵深防御 | PostgreSQL 连接复用和跨企业读写矩阵通过 |
| 10 | M1-10 | Web 企业/项目闭环 | 用户能登录、切换企业、管理成员和项目 |

### 4.3 M1 强制测试矩阵

身份：

- 正常、过期、未来 iat、错误 iss/aud、未知 kid、Key 轮换、IdP 超时。
- 登录、刷新、退出、撤销、并发刷新、Cookie 属性和 CSRF。
- 邮箱变更、同邮箱不同 Subject、Subject 相同不同 Issuer。

授权：

- 资源：企业、成员、邀请、项目、项目成员。
- 角色：未登录、非成员、Member、Admin、Owner、平台管理员。
- 动作：列表、读取、创建、修改、归档、恢复、邀请、改角色、移除。
- 结果：允许、403、隐藏资源 404、并发冲突 409。

数据库：

- PostgreSQL 原子 upsert。
- 最后 Owner 并发保护。
- version/If-Match 并发更新。
- RLS 连接池上下文清理。
- 事务回滚时审计/Outbox 不留半状态。

### 4.4 M1 验收门

- 使用真实 Keycloak Token 完成浏览器到 API E2E。
- 所有身份/授权测试在 CI 和 Staging 通过。
- auth、authorization、tenant 模块分支覆盖率 ≥90%；后端总体 ≥80%。
- Critical/High SCA/SAST 问题为 0，或有经批准且不影响认证的例外。
- API、审计和数据库证据可以证明跨租户访问为 0。
- 产品、技术、安全和 QA 四方签字后才可进入 M2。

## 5. M2：资产与对象存储闭环

只有 M1 ACCEPTED 后开始。

工作包顺序：对象 Key/威胁模型 → MinIO/OSS 适配端口 → 上传会话 → Multipart → 完成校验 → 下载授权 → 清理/对账 → 前端上传。

强制验收：

- 对象 Key 只能服务端生成。
- 1 KB、100 MB、1 GB、断点续传、取消、摘要错误、越权下载全部覆盖。
- DB 成功/OSS 失败、OSS 成功/DB 失败可幂等恢复。
- 预签名 URL 和临时凭证不进入日志。
- MinIO 开发 E2E 与阿里云 OSS Staging E2E 分开验收。

## 6. M3：Agent 注册与安全通信

只有 M2 ACCEPTED 后开始。

工作包顺序：协议契约 → 注册令牌 → CSR/证书 → 心跳/能力 → 禁用/吊销 → 本地状态 → 断线恢复。

强制验收：

- Agent 私钥只在本机生成并保持最小权限。
- Token 一次性消费并防重放。
- 仅主动出站连接。
- 证书轮换、吊销、时钟偏差和断网恢复通过。
- 不允许执行用户任意代码。

## 7. M4：任务与工作流最小闭环

只有 M3 ACCEPTED 后开始。

先仅实现 `artifact.copy.v1`，不扩展训练、模型或芯片适配。

工作包顺序：Job Schema → Job/Attempt/Lease → Temporal Signal/Timer → 原子分配 → 日志 → 取消/超时/重试 → 输出校验 → 审计。

强制验收：

- 任务创建幂等。
- Lease fencing 阻止旧 Agent 提交。
- Worker/API/Agent 重启后状态可恢复。
- 日志有序、可补拉、可脱敏。
- 20 次 E2E 成功率 ≥95%，失败均有诊断码。

## 8. M5：发布与可运营基线

范围：Staging、镜像、IaC、监控、告警、备份、恢复、回滚、安全扫描和 Runbook。

发布门：

- PostgreSQL PITR 演练满足 RPO/RTO。
- Keycloak Realm/数据库可恢复。
- MinIO/OSS 对象误删可恢复。
- 应用 15 分钟内回滚。
- 告警到达责任人并链接 Runbook。
- Blocker/Critical 为 0。

## 9. 每个工作包的强制交付物

进入 READY 前：

1. 一页范围说明：做什么、不做什么。
2. 验收标准，使用稳定编号。
3. API/事件/数据库变更草案。
4. 权限、审计、幂等、错误码说明。
5. 风险和回滚方案。
6. 测试数据与依赖环境说明。

进入 TESTS_RED 时：

1. 单元/集成/契约/E2E 测试清单。
2. 预期失败输出和失败原因。
3. 证明失败来自缺失功能，而不是测试环境损坏。

进入 REVIEWED 时：

1. 代码评审记录。
2. 架构偏差说明或 ADR。
3. 安全检查结果。
4. 迁移升级/回滚证据。
5. 覆盖率和未覆盖关键路径。

进入 ACCEPTED 时：

1. Staging 运行链接或证据包。
2. 验收标准逐项 Pass/Fail/Blocked。
3. 缺陷清单和例外审批。
4. 对应 Git Commit、镜像摘要和迁移版本。
5. 产品、技术、QA；安全相关切片还需安全签字。

## 10. 代码评审门禁

### 10.1 通用门禁

- PR 关联需求与验收编号。
- 测试必须能在未实现时正确失败。
- 禁止路由/依赖随意 commit；事务由应用服务控制。
- 数据库变更必须有迁移、约束、升级和回滚测试。
- OpenAPI 变更必须生成差异并标记兼容性。
- 日志不得包含 Token、Cookie、密钥、预签名 URL 或敏感 PII。
- 新依赖说明许可证、维护状态、漏洞和替代方案。

### 10.2 身份与租户附加门禁

- 不信任客户端传入的 user_id/organization_id 作为授权证据。
- 每个资源查询明确租户过滤或 RLS 证据。
- 认证失败、无权限和隐藏资源的响应语义一致。
- 并发和重放场景必须测试。
- 前端权限只改善体验，不能替代服务端授权。

### 10.3 Agent/任务附加门禁

- 命令和事件有 schema/version/idempotency key。
- Lease/Attempt/Fencing Token 全链路验证。
- 外部副作用可重试且不会重复提交。
- 任意代码执行和路径穿越测试必须存在。

## 11. 测试分层与门槛

| 层级 | 触发 | 门槛 |
|---|---|---|
| 单元测试 | 每次 PR | 领域规则、解析和状态机；快速且确定 |
| SQLite 测试 | 可选快速反馈 | 不可作为 PostgreSQL 行为验收证据 |
| PostgreSQL 集成 | 每次 PR | 约束、事务、并发、RLS、迁移 |
| 契约测试 | 每次 PR | OpenAPI/JSON Schema 兼容性 |
| 依赖集成 | 每次 PR 或 nightly | Keycloak、Redis、MinIO、Temporal |
| 浏览器 E2E | 合并前/nightly | 核心用户路径 |
| 安全与依赖扫描 | 每次 PR/nightly | Critical/High 阻断 |
| 性能/恢复 | 里程碑 | 达到该里程碑明确阈值 |

覆盖率不是唯一门槛：

- 后端总体行覆盖 ≥80%。
- auth/authorization/tenant/transaction 分支覆盖 ≥90%。
- 前端核心页面有组件测试和 E2E，不以单一首页测试代替。
- Go Agent 必须运行 race、断网、重启和文件权限测试。

## 12. 缺陷与例外管理

| 等级 | 处理规则 |
|---|---|
| Blocker | 立即停止里程碑，修复并重新全量验收 |
| Critical | 不得进入下一门；必须修复 |
| Major | 原则上当前门修复；延期需负责人、期限和风险接受 |
| Minor | 可进入 backlog，但必须关联版本 |

任何例外必须记录：问题、影响、临时控制、责任人、截止日期和批准人。口头接受无效。

## 13. 评审节奏

- 每个切片 READY 评审：开发前。
- PR 代码评审：实现后。
- 每周风险审查：只看 Blocker/Critical、依赖和范围变化。
- 每个里程碑验收：Staging 证据齐全后。
- 每月架构一致性审查：检查 ADR、文档、契约和代码偏差。
- 每季度灾备与安全复审：进入真实客户数据前必须执行。
