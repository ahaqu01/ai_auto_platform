# 多模型、多芯片 AI 工程化与交付平台概要

> 文档依据：《AI工程化平台_创业完善版_V2.pptx》第 4—18 页；开源项目与技术资料检索时间：2026-08-20。

## 1. 一句话定义

建设一套面向企业 AI 项目交付的工程基础设施：把自然语言/业务需求转化为可追溯的数据、模型、芯片、软件和硬件组合，并通过远程真实设备完成精度、性能、功耗、温度、稳定性和异常恢复验证，最终输出可采购、可验收、可升级、可运维的软硬件交付包。

它不是又一个“训练平台”，核心价值是解决从“模型可用”到“真实设备上的系统可交付”之间的工程鸿沟。

## 2. 平台目标与边界

### 2.1 近期目标（0—12 个月）

- 聚焦 1—2 个重复度高、指标明确、边缘部署刚需的行业，例如智能摄像头视觉算法和新能源预测边缘盒子。
- 将已有项目沉淀为数据模板、训练配方、模型—芯片兼容矩阵、部署包、测试用例、验收报告和标准报价。
- 建成可用的远程设备池，实现自动部署、自动测试、日志与视频回传、客户在线验收、OTA 和回滚。
- 让非核心创始人能够依照标准流程完成同类项目交付。

### 2.2 中期目标（12—24 个月）

- 支持客户和合作伙伴自助提交任务、选择方案、使用设备池、查看验收报告和管理已上线设备。
- 形成平台授权、设备运营和持续运维收入。
- 建立认证适配包、行业工作流和硬件套件生态。

### 2.3 长期愿景

形成连接创造者、企业、开发者、芯片厂商和制造伙伴的软硬件创意履约网络，使方案可以验证、购买、授权、分享和生产。

### 2.4 明确不做

- 第一阶段不做覆盖所有模型、所有芯片、所有行业的“万能平台”。
- 不自研通用标注工具、通用 Kubernetes、通用模型仓库或通用深度学习编译器。
- 不承诺任意模型均可全自动转换；不支持的算子、精度损失和厂商工具链缺陷必须进入人工专家兜底。
- 不把“模型转换成功”作为交付完成，只有验收指标通过才算完成。

## 3. 目标用户与核心场景

| 用户 | 核心诉求 | 平台输出 |
|---|---|---|
| 行业客户/集成商 | 快速验证 AI 方案并获得确定报价 | 可复现实机结果、验收报告、完整交付包 |
| 算法团队 | 少处理芯片工具链和设备差异 | 标准工作流、适配配方、自动基准测试 |
| 芯片/硬件厂商 | 扩大可运行模型与行业方案 | 认证适配包、兼容矩阵、性能基线 |
| 运维团队 | 批量管理现场设备 | OTA、灰度、监控、告警、回滚、审计 |
| 生态开发者（后期） | 发布和变现经验证方案 | 远程设备验证、授权、交易与交付渠道 |

首批建议场景：

1. 智能摄像头/边缘盒子的检测、分类、分割、跟踪、OCR、姿态等视觉应用。
2. RK3588 等边缘设备上的光伏/风电等时序预测。
3. 第二阶段再扩展轻量 VLM、中小 LLM；VLA/具身智能仅作为联合验证方向，不纳入首版通用承诺。

## 4. 核心业务闭环

1. **需求建模**：描述业务目标、输入数据、部署环境、预算、交付周期和验收阈值。
2. **数据工程**：接入、清洗、对齐、标注、质量分析、版本、权限和线上异常数据回流。
3. **模型与应用工程**：模型选型、训练/微调、组合编排、评估、量化、剪枝、蒸馏和失败诊断。
4. **目标硬件适配**：依据兼容矩阵选择芯片、系统、驱动、运行时和编译参数，生成候选部署包。
5. **远程实机验证**：自动预约设备、刷写/部署、注入测试数据，采集精度、延迟、吞吐、内存、功耗、温度和稳定性指标。
6. **验收与购买决策**：客户查看实时演示、测试证据、版本依赖、已知问题和报价，在线确认验收。
7. **交付与运营**：输出模型、SDK、容器/固件、应用组件、BOM、说明文档、测试报告，并进行 OTA、监控、灰度和回滚。
8. **资产回流**：将成功/失败结果沉淀为可复用配方、测试资产、交付模板和兼容矩阵。

## 5. 平台功能蓝图

### 5.1 门户与项目工作台

- 多租户、组织、项目、成员、RBAC、配额和审计。
- 需求表单与自然语言助手；自动生成技术方案草案，但关键承诺必须由工程师审批。
- 项目看板、里程碑、任务状态、成本、风险、验收和交付物管理。
- 客户只读/验收视图与供应商协作空间。

### 5.2 多模态数据工程

- 图像、视频、文本、语音、时序、传感器数据接入及元数据目录。
- 对象存储、数据集快照、血缘、版本、校验和、权限及生命周期管理。
- 数据清洗、去重、脱敏、质量规则、模态时间同步和语义对齐。
- AI 预标注、人工复核、主动学习、困难样本挖掘和线上数据回流。

### 5.3 模型与应用工程

- 实验跟踪、训练任务、模型注册、指标对比、审批与版本晋级。
- 视觉、预测、轻量 VLM/LLM 的模板化训练、微调和评估。
- RAG/Agent/多模型工作流作为应用编排能力，和底层模型工件分开管理。
- 模型卡、数据卡、依赖清单、许可证、安全扫描和可复现环境。

### 5.4 异构芯片适配

- 统一中间格式优先采用 ONNX；按目标硬件进入 TensorRT、RKNN、CANN/ATC、MagicMind、厂商 RISC-V 工具链等适配器。
- FP32/FP16/INT8/INT4 候选组合，自动进行校准、精度回归和性能基准。
- 算子支持分析、替代策略、图优化、编译日志归一化和失败分类。
- 维护“模型 × 芯片 × OS × 驱动 × 运行时 × 编译参数 × 输入规格”的兼容矩阵，而非仅记录“芯片支持”。

### 5.5 远程真实硬件实验室

- 设备入池、身份、标签、能力、健康状态、预约、独占锁和配额。
- 远程电源、串口、ADB/SSH、刷机、容器部署、固件升级和异常自动恢复。
- 摄像头/视频/传感器数据注入；画面、日志和结果实时回传。
- 外接功耗计和温度传感器；长稳测试、断网/断电恢复、资源泄漏测试。
- 测试环境指纹、步骤、输入、输出和原始证据不可变留档。

### 5.6 验收、交付与设备运营

- 验收模板、阈值、测试集、场景、重复次数和通过规则版本化。
- 自动生成 HTML/PDF 报告，记录精度、延迟 P50/P95/P99、吞吐、内存、功耗、温度、稳定性和异常恢复。
- 交付包生成：模型、运行时、容器/固件、SDK/API、配置、BOM、SBOM、部署说明、验收报告、已知问题及售后边界。
- OTA 分组、灰度、签名校验、失败回滚、监控告警和远程诊断。

### 5.7 工程资产库

- 数据模板、模型模板、训练配方、编译适配器、测试用例、验收规范、交付模板和报价规则。
- 每项资产包含版本、适用边界、来源、许可证、责任人、验证设备和历史成功率。
- 资产复用率、首次成功率、验收通过率和专家介入时长作为平台核心指标。

## 6. 可行性评估

### 6.1 总体结论

**工程上可行，商业上有条件可行，但必须以窄行业和受控硬件矩阵起步。**

约 70%—80% 的通用基础能力可由成熟开源组件和厂商 SDK 组合；真正需要自研、也是核心壁垒的约 20%—30% 包括：统一资产模型、适配器协议、模型—芯片兼容矩阵、设备池调度、实机测试协议、验收证据链、失败诊断和交付包生成。

首个可收费版本在已有算法和硬件经验基础上，8—10 人团队用 6—9 个月可以实现；覆盖 PPT 全部愿景通常需要 24—36 个月持续投入，而且长期需要芯片适配与设备运营团队。

### 6.2 分项可行性

| 模块 | 可行性 | 判断 |
|---|---:|---|
| 项目、权限、资产、工作流 | 高 | 成熟 Web、IAM、数据库和工作流技术可复用 |
| 多模态标注与版本 | 高 | Label Studio、对象存储、lakeFS/DVC 可组合 |
| 实验、训练、模型注册 | 高 | MLflow/ClearML/Kubeflow 已成熟 |
| NVIDIA/x86 推理 | 高 | ONNX Runtime、TensorRT、Triton/OpenVINO 生态完善 |
| RK3588 等单一边缘芯片适配 | 中高 | 厂商 SDK 可用，但版本与算子边界需固化 |
| 多国产芯片统一适配 | 中 | 工具链、驱动、算子、文档和版本差异大 |
| 自动精度/性能回归 | 中高 | 测试框架可自研，难点是基准数据和口径 |
| 无人值守刷机与异常恢复 | 中 | 强依赖设备外围控制和机房工程 |
| 任意模型全自动交付 | 低 | 不应作为承诺，必须设支持矩阵和人工兜底 |
| 创意交易/生产生态 | 中低 | 技术可做，成立与否主要取决于供需和履约网络 |

## 7. 关键难点与应对

### 7.1 异构芯片不是一个统一 API 问题

难点包括算子覆盖、量化校准、动态形状、精度漂移、内存布局、驱动/固件兼容、工具链许可证和日志不可比。应对方式：

- 明确认证矩阵，只支持经过验证的模型族、输入规格、芯片和版本组合。
- 采用插件式适配器，每个适配器独立镜像、独立版本、独立测试。
- 所有编译结果关联环境指纹和原始日志；失败进入分类队列而不是反复盲试。
- 与芯片厂商建立联合实验室和升级前置验证机制。

### 7.2 效果指标与芯片指标必须同时成立

量化或算子替换可能提高性能但降低业务精度。平台需要统一的“交付约束求解”：在精度下限、P95 延迟、吞吐、内存、功耗、温度、BOM 成本和风险之间选 Pareto 候选，而不是只追求单项跑分。

### 7.3 真实设备池的可靠性

设备会死机、断网、刷写失败、过热或被任务污染。每个工位建议具备远程 PDU/继电器、串口服务器、独立管理网口、摄像头、功耗计和温度采集；任务必须有超时、租约、清理、恢复镜像和人工接管机制。

### 7.4 多模态数据合规

视频、人脸、语音和工业数据可能涉及个人信息、商业秘密和跨境限制。必须实施租户隔离、最小权限、传输/静态加密、脱敏、水印、下载审批、保留周期、删除证明和全链路审计；私有化部署应从首版架构上支持。

### 7.5 开源许可证与供应链

AGPL 组件、厂商闭源 SDK、模型权重许可证和训练数据授权可能限制商业分发。应建立 SBOM、许可证策略和发布门禁；尤其需单独评估 openBalena 的 AGPL 条款和各芯片 SDK 的再分发条件。

### 7.6 平台容易被项目定制拖垮

所有新需求先判断能否形成可复用资产。建议设立“标准产品 / 可配置扩展 / 一次性定制”三级边界；一次性定制必须单独报价，且不得污染核心平台模型。

## 8. 同类开源项目调研

### 8.1 结论

不存在与目标平台完全同构的成熟开源项目。现有项目分别覆盖 MLOps、数据标注、编译推理、云边协同或设备管理。最接近的建设方式是“产品控制平面自研 + 开源能力组件化接入 + 厂商工具链适配”。

### 8.2 功能、架构和技术栈对比

| 项目 | 主要能力与架构 | 主要技术/部署 | 优势 | 短板及与本平台关系 |
|---|---|---|---|---|

| [MLflow](https://github.com/mlflow/mlflow) | Tracking Server + 关系型 Backend Store + Artifact Store；实验、模型注册、评估和 LLM 可观测 | Python/FastAPI、SQL、对象存储、Helm/K8s | 轻量、开放、中立、生态广，模型元数据接口清晰 | 编排、数据治理和边缘设备能力较弱；适合作为模型注册与实验标准层 |

| [KubeEdge](https://github.com/kubeedge/kubeedge) | CloudCore/EdgeCore 云边架构，扩展 Kubernetes 到边缘；应用、设备和元数据同步 | Go、Kubernetes、WebSocket、MQTT、CRD | 弱网自治、云边可靠通信、边缘应用与设备管理成熟 | AI 模型编译、精度验证、验收和交付资产需自研；适合规模化现场设备控制面 |
| [Sedna](https://github.com/kubeedge/sedna) | 基于 KubeEdge 的边云协同 AI，支持联合推理、增量/联邦/终身学习 | Python/Go、KubeEdge、主流训练框架 | 边云协同训练与推理理念贴合，能参考数据回流和联合推理设计 | 社区和产品成熟度不及核心 KubeEdge；不覆盖异构芯片交付和远程实验室，可选择性借鉴而非强依赖 |
| [openBalena](https://github.com/balena-io/open-balena) | 后端服务 + balenaOS + CLI + VPN，面向容器化 IoT 设备群 | 容器、VPN、API、专用设备 OS | 设备开通、容器更新、远程访问和日志成熟 | 开源版主要依赖 CLI、生态与许可证需评估；要求 balenaOS，对已有国产板卡系统侵入较强 |
| [NVIDIA Triton](https://github.com/triton-inference-server/server) | 模型仓库 + 多后端 + HTTP/gRPC/KServe 协议；并发、批处理、ensemble 和指标 | C++、Python backend、TensorRT/ONNX/OpenVINO 等、容器 | NVIDIA/服务器推理性能和框架支持强，可作为中心推理与基准环境 | 不支持多数国产 NPU 工具链，不负责训练、设备 OTA 和验收；不应当作统一芯片抽象层 |
| [Apache TVM](https://github.com/apache/tvm) | 高层模型到 IR、图/算子优化、代码生成和轻量运行时 | C++/Python、编译器 IR、多硬件 backend | 可扩展编译栈和自动调优能力强，对新硬件有研究与共建价值 | 集成和芯片后端开发门槛高，不能替代厂商生产工具链；首版仅在明确芯片合作场景采用 |
| [OpenVINO](https://github.com/openvinotoolkit/openvino) | Frontend 读模型、Core 统一 API、硬件 Plugin 编译执行 | C++/Python、ONNX 等前端、Intel CPU/GPU/NPU 插件 | 插件式设备架构清晰，CPU/Intel 生态成熟，值得借鉴适配器设计 | 硬件覆盖主要围绕 Intel，无法直接解决国产芯片矩阵 |

### 8.3 可借鉴的设计原则

- 借鉴 ClearML 的“低侵入 SDK + Agent”模式，现有算法代码只需最小修改即可纳管。
- 借鉴 MLflow 的“元数据与大工件分离、接口可插拔”模式。
- 借鉴 Kubeflow/KubeEdge 的声明式资源与控制器协调模式，但 MVP 不引入其全部复杂度。
- 借鉴 OpenVINO 的 Frontend/Core/Plugin 分层，将统一任务协议与厂商实现解耦。
- 借鉴 Triton 的模型仓库、标准推理协议和可观测指标。
- 借鉴 lakeFS 的不可变快照与回滚语义，将测试输入和交付证据固化。
- 借鉴 openBalena 的设备开通、VPN 和 OTA 思路，但保留对 Ubuntu、OpenEuler、Buildroot/Yocto 和厂商 OS 的适配能力。

## 9. 推荐落地架构

### 9.1 架构原则

- **模块化单体起步**：门户、项目、资产、验收、交付先使用一个后端和清晰领域模块，避免早期微服务运维负担。
- **重任务异步化**：训练、编译、刷机、测试均通过队列和 Worker/Agent 执行。
- **控制平面与数据平面分离**：平台只保存元数据、状态和策略；大文件进入对象存储，计算在 GPU/编译/设备节点执行。
- **统一协议，不统一实现**：定义标准输入输出、状态、指标和错误码；各芯片适配器保留厂商原生工具链。
- **证据优先**：每次验收都能追溯到代码、数据、模型、容器、驱动、设备和测试用例版本。
- **私有化优先兼容**：SaaS 与客户本地部署使用同一套容器化架构。

### 9.2 逻辑分层

| 层 | 推荐实现 |
|---|---|
| Web 门户 | Vue 3 + TypeScript + Vite + Ant Design Vue；客户门户和工程工作台共用组件 |
| API/领域后端 | Python 3.12 + FastAPI + SQLAlchemy + Pydantic；模块化单体，OpenAPI-first |
| 身份与权限 | Keycloak（OIDC/OAuth2/SAML）+ 平台 RBAC/项目 ABAC；企业可对接 LDAP/AD |
| 工作流 | MVP 使用 Temporal；其持久化工作流适合长时间、可重试、含人工审批的编译/设备任务。纯数据/训练 DAG 可接 ClearML 或后期接 Kubeflow Pipelines |
| 消息与缓存 | Redis（缓存、短队列、锁）；设备遥测规模增长后使用 NATS JetStream 或 Kafka；MQTT 用 EMQX/Mosquitto |
| 元数据 | PostgreSQL 高可用；TimescaleDB 或 VictoriaMetrics 保存设备与测试时序指标 |
| 对象/制品存储 | MinIO/S3，保存数据集、模型、日志、视频、报告和交付包；Harbor 保存容器镜像并做签名/漏洞扫描 |
| 数据标注与版本 | Label Studio + lakeFS（或小规模先用 DVC）+ 自研数据目录/质量/血缘服务 |
| 实验与模型 | 建议 MVP 二选一：ClearML（功能一体化）或 MLflow（轻量开放）。已有训练团队若工具分散，优先 MLflow；希望快速获得任务调度和数据能力，优先 ClearML |
| 计算调度 | MVP 训练机/编译机运行 Docker Agent；达到多租户、多 GPU 和弹性需求后迁移 Kubernetes + NVIDIA GPU Operator + Volcano/Kueue |
| 模型格式与推理 | PyTorch/ONNX 为主；中心/NVIDIA 使用 TensorRT + Triton；通用 CPU 使用 ONNX Runtime/OpenVINO；边缘端按芯片使用原生 runtime |
| 边缘设备 | 自研轻量 Edge Agent（Go）负责注册、任务、日志、指标和升级；大规模现场运营引入 KubeEdge。实验室设备通过 Lab Controller 管理电源、串口、刷机和仪表 |
| 可观测性 | OpenTelemetry + Prometheus + Grafana + Loki + Tempo；Sentry 捕获前后端异常；Alertmanager/企业微信告警 |
| DevSecOps | GitLab CE/GitHub Enterprise、GitLab CI/Argo CD、Trivy、Syft/Grype、Cosign、Vault；基础设施用 Ansible + Terraform/OpenTofu |

### 9.3 核心自研服务

1. **Delivery Orchestrator**：把需求、数据、训练、编译、实机测试、审批和交付串成可恢复工作流。
2. **Adapter SDK**：定义 `inspect → convert → calibrate → compile → package → benchmark → diagnose` 插件接口。
3. **Compatibility Registry**：存储完整环境指纹、指标、失败原因、适用边界和认证状态。
4. **Lab Scheduler/Controller**：按设备能力、租户、预约和健康状态分配真实设备，操作 PDU、串口、刷机和采集仪表。
5. **Acceptance Engine**：按版本化规则计算通过/失败，固化原始证据并生成签名报告。
6. **Delivery Packager**：输出可验证、可安装、带 SBOM/签名/许可证清单和回滚方案的交付包。

### 9.4 关键数据对象

`Organization / Project / Requirement / DatasetSnapshot / Experiment / ModelVersion / ApplicationWorkflow / TargetProfile / BuildRecipe / Device / LabSlot / TestSuite / TestRun / Metric / AcceptanceDecision / DeliveryBundle / Deployment / Incident`

每个 `DeliveryBundle` 必须关联唯一的代码提交、数据快照、模型摘要、适配配方、容器摘要、设备指纹、测试套件和验收决策。

## 10. 分阶段实施方案

### 阶段 0：产品边界与标准（第 0—1 个月）

- 选定两个首批场景和不超过三类目标硬件，例如 NVIDIA GPU、RK3588、一个合作国产 AI 芯片。
- 整理已有三个项目，统一需求、模型、数据、环境、指标、故障和交付物结构。
- 定义 Adapter SDK、设备协议、验收指标口径和兼容矩阵 Schema。
- 建立 20—30 条黄金测试用例和 3 套标准报价模板。

**退出条件**：每个场景均有明确输入、输出、支持边界、基线设备和验收阈值。

### 阶段 1：内部 MVP（第 2—4 个月）

- 上线组织/项目、对象存储、实验/模型注册、工件追溯和基础工作流。
- 完成 NVIDIA、RK3588 两个适配器和基础精度/性能回归。
- 搭建 6—10 台/块设备的实验室，支持预约、远程部署、日志回传和硬重启。
- 自动生成首版验收报告和交付清单。

**退出条件**：至少两个历史项目可由平台全流程复现；同一配方重复运行结果可解释。

### 阶段 2：可收费交付版（第 5—8 个月）

- 加入客户门户、审批、在线演示、报告签名、交付包、报价和售后边界。
- 完成功耗/温度/长稳/断网/断电/回滚测试。
- 加入第三类芯片适配器和人工专家工单。
- 建立监控、备份、灾备、安全审计和 SLA。

**退出条件**：3—5 个同类付费客户；资产复用率 ≥50%；非创始人可完成至少 60% 标准流程；实机验收证据可审计。

### 阶段 3：平台化与设备运营（第 9—15 个月）

- Kubernetes 化计算层，引入队列配额、弹性 Worker 和多租户资源隔离。
- 现场 Edge Agent、OTA 灰度、监控、远程诊断和回滚。
- 客户自助设备池、适配包认证、使用计量和订阅计费。

**退出条件**：10+ 同类客户或 100+ 在线设备；核心资产复用率 ≥70%；无创始人交付比例 ≥80%。

### 阶段 4：生态化（第 16—24 个月）

- 认证方案市场、合作伙伴工作流、硬件套件和授权交易。
- 在法律、质量和履约体系成熟后再开放创意分享与生产合作。

## 11. 硬件与机房建议

以下为初创期可落地配置，不应一次性按终局规模采购。训练峰值优先租用公有云 GPU，稳定高利用率后再购置。

### 11.1 MVP（8—10 人、3—5 个并发项目）

| 用途 | 数量 | 建议配置 | 说明 |
|---|---:|---|---|
| 管理/控制节点 | 3 | 16—24 核 CPU、64—128 GB RAM、2×1.92 TB 企业 SSD、双 10GbE | 组成 3 节点虚拟化/轻量 K8s 集群，承载 API、PostgreSQL、Temporal、监控等；避免单点 |
| GPU 训练/验证节点 | 2 | 每台 32—64 核 CPU、256 GB RAM、2× NVIDIA L40S 48GB 或按模型选 2× RTX 6000 Ada、系统盘 2×1.92 TB、缓存盘 2×3.84 TB NVMe、25GbE | 视觉/预测/轻量 VLM 足够；大型 LLM 训练不建议自建 |
| 对象存储节点 | 3 | 每台 16 核、64 GB、8×12/16 TB 企业 HDD、2×3.84 TB NVMe 缓存、双 25GbE、HBA/JBOD | MinIO 纠删码；有效容量按原始容量约 50%—65% 规划，必须另有备份 |
| CI/编译节点 | 2 | 24—32 核、128 GB、2×3.84 TB NVMe、10/25GbE；其中一台可带 NVIDIA T4/L4 | 隔离不同厂商 SDK 和编译镜像，避免污染训练节点 |
| 运维/备份节点 | 1 | 16 核、64 GB、4×大容量盘；另配离线/异地备份 | 日志归档、备份、镜像缓存、堡垒机可拆分虚拟机 |
| 实验室设备工位 | 6—10 | NVIDIA Jetson/目标摄像头、RK3588、国产芯片开发板各 2—3 套 | 同型号至少两套，一套服务、一套故障/升级验证 |

初期物理服务器合计 **11 台左右（其中 3 台存储）**。若资金紧张，可将控制、CI、监控虚拟化合并为 3 台服务器，并将对象存储先缩为 3 台小容量节点，物理服务器降至 **8 台**；但数据库、对象存储和备份仍不可放在单机上。

### 11.2 成长期（20—30 人、10—20 并发项目）

- 3 台独立 Kubernetes 控制节点。
- 4—8 台 GPU 计算节点；按任务拆为训练池、推理基准池和 LLM/VLM 池。
- 4—6 台 CPU/编译/流水线节点。
- 4—6 台对象存储节点，原始容量 0.8—2 PB，25/100GbE。
- 3 台数据库/中间件节点，2 台可观测性节点，2 台备份节点。
- 30—100 个远程实验工位，并按故障域分柜/分电源。

约 **18—29 台服务器**，具体数量由 GPU 利用率、数据保留周期和客户并发决定，而不是用户数直接决定。

### 11.3 设备实验室外围

- 每 8—12 个工位配置可远程控制 PDU；关键设备支持继电器硬重启。
- 1—2 台串口服务器、独立管理交换机、USB/HDMI 视频采集、可编程网络故障注入。
- 每工位可计量插座/功耗计和温度探头；高功耗 GPU 使用机柜级 PDU 计量。
- 恢复镜像服务器、固件仓库、烧录器、备用 SD/eMMC/NVMe 和 ESD 防护。
- 实验室视频监控只用于设备状态，不采集不必要的人员信息。

### 11.4 供电与散热

- MVP IT 负载按 15—25 kW 估算，成长期按 GPU 型号重新核算；机房制冷必须按峰值而非平均值设计。
- 双路市电优先；UPS 至少支撑 15—30 分钟并接入监控，关键存储和控制节点双电源。
- GPU 服务器机架注意功率密度，单柜不宜在未经核验的情况下堆满高功耗 GPU。

## 12. 网络方案

### 12.1 网络分区

- **办公/研发网**：开发者终端，不直接访问设备管理口。
- **服务区**：API、数据库、对象存储、CI、监控，按安全组细分。
- **GPU/存储数据网**：25GbE 起步；大量视频和训练数据时升级 100GbE，启用 LACP 和巨帧需端到端验证。
- **实验设备业务网**：设备运行和测试数据流量。
- **带外管理网**：BMC/IPMI、PDU、串口服务器，只能经堡垒机和 MFA 访问。
- **访客/客户演示区**：仅通过网关访问授权会话，禁止横向访问内部资源。

### 12.2 出入口与远程接入

- 两家运营商链路，企业专线建议主 1—2 Gbps、备 500 Mbps—1 Gbps；大视频数据上传按实际峰值扩容。
- 公网入口置于 WAF/反向代理之后，TLS 1.2+，API 限流、防重放和 DDoS 基础防护。
- 员工使用 WireGuard/零信任接入 + MFA；设备建立双向 mTLS，不开放公网 SSH。
- 设备出站连接控制面，通过消息通道领取任务；客户交互使用短期令牌和会话审计。
- 大工件上传使用对象存储预签名 URL、分片、断点续传和校验和。

### 12.3 带宽估算

`所需带宽 ≈ 并发视频路数 × 单路码率 × 1.3 + 工件上传峰值 + 备份窗口流量`。例如 20 路 8 Mbps 视频约需 208 Mbps（含 30% 余量），再加模型/数据上传和备份，1 Gbps 主链路是合理起点。

## 13. 运维、安全与可靠性

### 13.1 平台维护工具

- GitLab/GitHub 管代码与评审；GitLab CI 或 GitHub Actions 构建测试。
- Harbor 管镜像，Trivy/Syft/Grype 做漏洞和 SBOM，Cosign 做镜像/交付包签名。
- Argo CD 做 GitOps 发布；Ansible 管服务器和设备基础配置；Terraform/OpenTofu 管云资源。
- Prometheus + Grafana 看指标，Loki 看日志，Tempo 看链路，OpenTelemetry 统一采集。
- Sentry 管应用异常，Alertmanager 对接企业微信/短信；所有告警必须有负责人和 Runbook。
- Vault 管密钥，Keycloak 管身份；堡垒机记录高权限操作。
- PostgreSQL 使用自动备份和时间点恢复；MinIO 做版本/对象锁，另有异地不可变备份。

### 13.2 SLO 建议

- 首年平台控制面月可用性目标 99.5%，成熟后提升至 99.9%。
- 元数据 RPO ≤15 分钟、RTO ≤2 小时；对象工件 RPO ≤24 小时、RTO ≤8 小时。
- 实验设备不承诺单设备高可用，承诺同能力设备池的可用率和预约补偿。
- 所有 OTA 必须支持分批、健康检查、自动暂停和一键回滚。

### 13.3 安全基线

- 租户级逻辑隔离，敏感客户支持独立资源池或私有化部署。
- 代码、模型、容器、固件和交付包均进行摘要、签名、漏洞扫描和审批。
- 训练/编译任务在受限容器中运行，默认无特权、限制出网、限制主机挂载；设备刷机 Worker 单独隔离。
- 原始数据下载、外发、删除和管理员操作写入不可篡改审计日志。
- 每季度恢复演练，每半年渗透测试；建立漏洞响应、密钥轮换和离职权限回收流程。

## 14. 团队配置

首个可收费版本建议 9—12 人：

- 产品负责人/行业解决方案 1 人。
- 平台架构/技术负责人 1 人。
- 后端/工作流工程师 2 人。
- 前端工程师 1 人。
- MLOps/训练平台工程师 1—2 人。
- 芯片部署/编译工程师 2 人（按目标芯片增加）。
- 设备/嵌入式/实验室工程师 1—2 人。
- DevOps/SRE/安全 1 人（早期可兼任，但上线收费后需专职）。
- 测试/质量工程师 1 人。

算法专家作为共享角色参与模板、精度回归和疑难兜底。随着芯片和行业增加，适配工程师与测试工程师应线性增加；平台核心研发不应被客户现场定制长期占用。

## 15. 成本与采购策略

- **先租后买**：低利用率、峰值型 GPU 训练使用公有云；利用率连续 3 个月超过 50%—60% 再评估自购。
- **算存分离**：数据和模型集中在对象存储，GPU 节点只保留高速缓存，便于扩容与故障替换。
- **硬件池按收入扩展**：每新增芯片类型至少采购两套；没有客户/厂商共建承诺的芯片不进入认证矩阵。
- **配置而非定制**：交付报价拆为一次性工程费、设备/平台持续服务费和超出标准边界的定制费。
- 建议以人力为最大预算项，硬件一次性投入保持在可支持 6—9 个月产品验证的范围，避免在市场成立前采购大型 GPU 集群。

## 16. 关键指标

### 产品与商业

- 同类付费客户数、从需求到首次实机结果的周期、报价转化率。
- 一次性交付收入、平台/设备持续收入、毛利率、续费率。

### 工程复用

- 复用资产步骤数 / 总步骤数。
- 无创始人交付比例、专家介入工时、一次编译成功率。
- 模型—芯片配方复用次数、适配器自动诊断覆盖率。

### 质量与运营

- 实机验收通过率、基准结果波动、OTA 成功/回滚率。
- 设备池可用率、平均恢复时间、任务排队时间和设备利用率。
- 线上故障率、数据/模型漂移告警闭环时间。

## 17. 主要风险与决策门

| 风险 | 早期信号 | 对策/决策门 |
|---|---|---|
| 范围过大 | 每个客户都引入新行业/芯片 | 任何新芯片需有付费客户或厂商共建，且预计 6 个月内复用 ≥3 次 |
| 自动化名不副实 | 大量任务仍需创始人手工处理 | 记录每个手工步骤；连续 3 次出现则产品化或明确为收费专家服务 |
| 开源拼装但体验割裂 | 用户跨多个 UI 和账号 | 自研统一门户、SSO、统一任务状态和资产链接，第三方 UI 仅作为高级入口 |
| 结果不可复现 | 同一模型多次跑分差异大 | 固化环境指纹、预热、重复次数、设备温度和统计口径 |
| 设备池故障频繁 | 任务大量卡死、需现场重启 | 同型号冗余、硬重启、恢复镜像、租约超时和每日健康巡检 |
| 数据与模型合规 | 权属不清、客户要求删除 | 数据/模型准入清单、授权证明、保留策略、删除证明和私有化方案 |
| 平台投入早于收入 | 功能很多但无重复客户 | 每阶段以付费客户、复用率、非创始人交付比例作为继续投资门槛 |

## 18. 最终建议

1. 公司真正的产品不是“六大功能菜单”，而是**经过实机验证的可交付结果和不断积累的工程资产**。
2. 首版只选择两个行业场景、三类以内硬件和有限模型族，先证明周期下降、复用率上升和客户愿意付费。
3. 采用“模块化单体控制平面 + 异步 Worker/Agent + 插件式芯片适配器 + 独立设备实验室”的架构，规模成立后再全面 Kubernetes 化。
4. 通用能力优先集成开源项目；将研发集中在兼容矩阵、设备池、验收引擎、失败诊断和交付包，这些才是差异化和数据飞轮所在。
5. 把支持边界、版本依赖、已知问题、售后范围和回滚方案写进每个交付包。平台的可信度来自可验证和可追溯，而不是“全自动”的宣传。
6. 用 6—9 个月完成可收费版本，以 3—5 个同类付费客户、≥50% 资产复用率和非创始人可交付作为下一阶段投资依据。
